# Чеклист переноса RoadWitsServer: FastAPI/Python → Rust (tonic/sqlx)

Статус: рабочий прототип. Компилируется (`cargo build --workspace`, офлайн —
`.sqlx/` закоммичен), поднимается на пустой Postgres (миграции применяются
сервером при старте), и весь основной сценарий проверен вживую через
grpcurl (см. "Что реально проверено" ниже) — не только "должно работать по
чтению кода".

## 1. Принятые решения по ТЗ

- [x] **Транспорт — только gRPC.** REST/gRPC-Gateway не переносился и не
      добавлялся. Клиент — тоже Rust, ходит в API напрямую через
      `roadwits-proto` (сгенерированные tonic-клиенты). Веб-UI нет и не
      предполагается.
- [x] **orders/payments выпилены полностью.** Ни таблиц, ни роутеров, ни
      сервисов, ни ЮKassa-интеграции. `User.payment_info` (JSON-поле,
      которое админ мог руками указать при выдаче лицензии — способ оплаты,
      номер квитанции и т.п., без вебхуков и обработки платежей) — оставлено,
      потому что это отдельная от orders/payments вещь: обычное
      JSON-поле лицензии, не работающий платежный флоу.
- [x] **Стек:** tonic + prost, tokio, sqlx/postgres с
      `sqlx::query!`/`query_as!` (компилируемые проверки запросов — реально
      проверено против живой БД, не просто заявлено), tracing +
      tracing-subscriber, jsonwebtoken.


## 3. Проверка бизнес-правил (перенесены и проверены вживую)

- [x] Login: порядок проверок product_key → is_blocked → license_until →
      device slot, именно в этом порядке (важно: следующая проверка
      предполагает, что предыдущая пройдена).
- [x] Device limit (`max_devices`, 1..3) — блокирует логин с нового
      устройства при исчерпанных слотах, снимается `ResetDevice` от админа.
      Проверено: 4-е устройство отклонено, после ResetDevice — принято.
- [x] JWT содержит только `sub` (user id) + `device` (fingerprint) + `exp` —
      без email и прочего. При каждом запросе fingerprint из токена
      сверяется с реально привязанными устройствами в БД — значит
      `ResetDevice` мгновенно инвалидирует все старые токены этого
      устройства, даже если сам JWT ещё не истёк.
- [x] Роли: student (по умолчанию) / editor (главы и задания, но НЕ
      порядок глав) / admin (всё). Проверено: editor получает
      PermissionDenied на попытке сменить `order` главы.
- [x] Admin не может удалить сам себя (`DeleteLicense`). Проверено.
- [x] Задание: минимум 2 варианта ответа, ровно один правильный —
      проверяется до записи в БД, атомарно (см. раздел 4, баг №2).
- [x] Дружба: нельзя добавить себя, нельзя дублировать заявку, принять
      может только адресат, разорвать — любая из сторон. Проверено полным
      циклом send → accept → leaderboard.
- [x] Leaderboard: сумма `settings.quiz_stats.*.answered` по себе + всем
      принятым друзьям, сортировка по убыванию. Проверено (и именно тут
      нашелся баг №3, см. ниже).
- [x] `settings`/`payment_info` — free-form JSON, но не "вообще без
      проверки": лимиты на глубину/размер/количество ключей и запрет
      строк, похожих на код/разметку (`<script>`, `javascript:`,
      `onerror=` и т.п.) — тот же набор правил, что и в
      `app/schemas/safe_json.py`.

## 4. Баги, найденные и исправленные ЖИВЫМ тестированием

Компиляция (тем более с `sqlx::query!` против настоящей схемы) ловит опечатки
в SQL и несовпадения типов, но не логические баги на границе форматов.
Три штуки нашлись только когда сервис реально дернули через grpcurl:

1. **Синтаксис `"column!"` вне макроса.** В `chapter_repo.rs` список глав
   строился как runtime-SQL строка (не через `query_as!`, потому что запрос
   динамический — конкатенация WHERE), и туда по инерции попал
   macro-only синтаксис `as "question_count!"` (NOT-NULL override для
   `sqlx::query!`). Postgres создал колонку с буквальным именем
   `question_count!`, `FromRow` не находил `question_count` → 500-ка на
   каждый `ListChapters`. **Урок:** этот синтаксис имеет смысл только
   внутри `query!`/`query_as!`, никогда — в сырых строках.
2. **Неатомарная запись создавала "осиротевшие" строки.** Создание главы/
   вопроса делало `INSERT`, затем отдельным запросом перечитывало полную
   строку (чтобы посчитать `question_count`/подтянуть `created_by_email`).
   Если второй запрос падал (как в баге №1) — INSERT уже закоммичен,
   получалась пустая глава без данных, доступная только прямым SQL.
   Для вопросов было хуже: `CreateQuestion` инвалидную комбинацию ответов
   (например, два "правильных") успевала записать вопрос ДО валидации
   ответов, оставляя вопрос без единого варианта в БД. **Исправлено:**
   всё создание/обновление главы и создание/обновление вопроса+ответов
   теперь в одной транзакции (`pool.begin()`/`commit()`); проверено, что
   при отклоненном запросе строк не остается вообще.
3. **`google.protobuf.Struct` хранит числа только как `double`.** Отправили
   `settings.quiz_stats.chapter2.answered = 15` (int), после round-trip
   через proto Struct в БД легло `15.0`. `serde_json::Number::as_i64()` на
   float-typed числе молча возвращает `None` — `Leaderboard` показывал 0
   очков вместо 15, без единой ошибки в логах. **Исправлено:** конвертер
   `pbstruct.rs::number_to_json` теперь восстанавливает целые JSON-числа для
   любого `f64` без дробной части в пределах `i64`. Это системное
   ограничение `Struct`, а не разовая опечатка — стоит держать в голове при
   добавлении новых числовых полей в settings.

Из этого стоит сделать вывод для дальнейшей разработки: **любой новый
gRPC-метод, трогающий settings/payment_info или делающий больше одной
операции записи, нужно гонять через grpcurl (или интеграционный тест) до
мержа**, компиляция одна такие вещи не ловит.

## 5. Осознанные отступления от буквального 1:1

- **`Me` теперь отдает `product_key`** (в оригинале — нет). Раз клиент и
  так его знает (иначе не смог бы залогиниться), скрывать было
  избыточно, а для gRPC-клиента (не браузер, no XSS-поверхности) это не
  добавляет риска. Если это принципиально — легко убрать обратно.
- **`test_results`/TestResult** перенесен как таблица (для совместимости
  схемы на случай, если где-то есть прямые SQL-обращения), но не как
  gRPC-метод — потому что и в оригинале это была неподключенная модель
  (ни один роутер её не вызывал). Если это открытие бага в оригинале
  (результаты тестов должны были быть доступны, но роут забыли добавить) —
  стоит явно решить, добавлять ли `SubmitTestResult`/`ListTestResults` в
  `ContentService`, сейчас это не пытались угадать.

## 6. Что НЕ сделано (осознанно, вне текущего эффорта)

- [ ] **Логирование/метрики уровня прод.** Сейчас `tracing` настроен на
      базовый `info`-уровень через `RUST_LOG`. Структурированные access-логи
      на каждый RPC (метод, код ответа, latency) не добавлены —
      несложно навесить через `tonic` interceptor/middleware слой, но не
      было в ТЗ явно.
- [ ] **TLS.** Сервер поднимается как обычный `h2c` (plaintext HTTP/2).
      Если клиент и сервер не в одном доверенном периметре — нужен
      `tonic::transport::ServerTlsConfig` (сертификаты) до продакшена.
- [ ] **Rate limiting / abuse-защита на Login.** В оригинале её тоже не
      было — не регрессия, но раз product_key это единственный секрет и
      brute-force пространство большое (24 символа из 32-символьного
      алфавита), лишним не будет, если посчитаете нужным.
- [x] **Docker/деплой-конфиг.** Multi-stage `Dockerfile` (сборка в
      offline sqlx-режиме, `.sqlx/` уже закоммичен → не нужен живой
      DATABASE_URL на этапе сборки), `docker-compose.yml` (db + app,
      структура 1:1 с тем, что было в легаси) и `.env.example`.
      Healthcheck на app — через `grpc_health_probe` (сервер уже
      регистрирует `grpc.health.v1`, см. `main.rs`), а не HTTP, как было
      в оригинале на FastAPI. Не проверено живой сборкой образа (нет
      Docker в среде, где это писалось) — стоит прогнать `docker compose
      up --build` перед тем, как полагаться на это в проде.
- [x] **Интеграционные тесты как код.** Добавлены
      `crates/roadwits-server/tests/business_rules.rs` (login: порядок
      проверок product_key → is_blocked → license_until → device slot;
      device limit + ResetDevice, включая мгновенную инвалидацию токена;
      создание вопроса — отклонение невалидных наборов ответов БЕЗ записи
      осиротевшей строки, регресс-тест на баг №2; полный цикл
      дружбы + лидерборд) и `tests/grpc_role_checks.rs` (editor не может
      поменять order главы, но может остальное; admin не может удалить
      сам себя, но может остальных; не-admin не может создать лицензию) —
      идут через `#[sqlx::test]`, каждый тест поднимает свою БД из
      `../../migrations` и не требует Docker/testcontainers, только
      Postgres по `DATABASE_URL`. Плюс юнит-тесты в `util/pbstruct.rs` на
      баг №3 (округление int/float при round-trip через `Struct`).
      **Не проверено `cargo test` в среде, где это писалось** — доступный
      там `rustc`/`cargo` 1.75 слишком стар для текущих версий
      транзитивных зависимостей (`edition2024`), и обновить его не вышло
      (сеть ограничена, `rustup`/`static.rust-lang.org` недоступны).
      Тесты написаны и вычитаны построчно против реальных сигнатур
      `repo`/`service`/`grpc` слоёв, но перед тем как полагаться на них —
      прогони `cargo test` (нужен `DATABASE_URL`, см. `.env.example`) в
      обычном окружении разработки.
- [ ] **Пагинация в ListLicenses/ListChapters.** Оригинал отдавал списки
      целиком, порт сохранил это поведение 1:1 — если объемы вырастут,
      это будет узким местом что там, что тут.
